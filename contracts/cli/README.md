# Installed CLI contracts

The local MVP contracts were adopted on 2026-10-13, following exact help/version
approval on 2026-10-12. Snapshots are intentional UTF-8 bytes with final newlines;
acceptance compares streams and exit codes without regenerating baselines.

Installed user commands are help/version, interactive init, configuration validation,
doctor, explicit provider tests, historical status and foreground start for webhook,
SMTP and mixed configurations. No arguments emit `no-arguments.stderr` with exit 2.
Invalid/duplicate/extra invocation words emit `invalid-invocation.stderr`, empty
stdout and exit 2. Helpers below are private child protocols. No service is installed.

## Configuration-validation addition (2026-10-13)

`config validate --config <absolute-path>` accepts exactly one config option before,
between or after the two command words. Unknown/duplicate flags, extra values,
relative or non-Unicode paths fail before file access with the invocation diagnostic.
`config validate --help` (help before/between words also accepted) loads no resources.
Global help now lists this command. Webhook validation succeeds with schema/cluster/
count output; invalid config/resources or unsupported SMTP scope exit 2 with the
corresponding static stderr snapshot and empty stdout. This finite command performs no monitoring.

## SMTP-validation addition (2026-10-13)

Configuration validation now supports webhook, SMTP and mixed configs. Success
with SMTP reports `smtp_permissions=approved`. A denied/mismatched current pair
returns `config-permission.stderr`, empty stdout, exit 3; config/resource failure
still uses `config-invalid.stderr`, exit 2. The earlier unavailable-SMTP diagnostic
is retired. No network/SMTP submission or state inspection occurs.

## Historical-status addition (2026-10-23)

`status --config <absolute-path>` accepts one config option before or after the
command. `status --help` or `--help status` reads no resources. Status parses config
metadata without resolving providers, credentials or identity. It reads existing
closed schema-4 or schema-5 state only; the current supported database basename is
`state.sqlite3`. It creates/migrates/repairs nothing and requires the existing lock
and exclusive ownership. Status while monitoring is busy, not a live health view.

Success: stdout only, exit 0, historical state/process-unknown/checkpoint and sampled
queue/capacity/retention fields. Missing checkpoint gives `age_seconds=unknown
stale=true`; invalid or future checkpoint fails. `queued` counts sampled pending
rows, `retrying` is the subset with a latest transient failure, `due` is the due
pending subset. Samples truncate at configured limits; do not treat counts as totals.
Capacity probes stop at their configured limit plus one. No IDs or destinations are
printed. Busy/missing/unsafe/unsupported/query failures use their respective static
stderr snapshots, empty stdout, exit 1. Config/grammar failures retain exit 2.

SQLite busy waiting and cooperative SQL VM interruption use the configured query
timeout. Filesystem calls have no universal hard deadline. Baseline files are
intentional compatibility records and never regenerated by tests.

## Private webhook child handler

The exact internal invocation `--internal-provider-v1 webhook` consumes a bounded
length-prefixed stdin frame and emits only the sanitized provider acknowledgment.
Malformed input exits 2 with empty stdout/stderr. Extra arguments retain normal
invalid-invocation behavior. This is a versioned parent/child protocol, not a user
command or provider-test interface; help and supported command baselines are unchanged.

The handler requires HTTPS, a UUID-v4 public ID matching the JSON payload and
explicit bounded timeout/field sizes. It does not read config/environment resources
or open state. The supervising parent must enforce the total wall-clock deadline
and child cleanup, including DNS/TLS stalls. Installed foreground send/restart now
has controlled verified-TLS acceptance; malformed-input checks alone do not prove delivery.

## Private bound SMTP child handler

The exact invocation `--internal-provider-v1 smtp-starttls` consumes the existing
bounded eight-field provider/profile, trust, credentials, envelope, frozen-message
and timeout frame. It performs no config, environment or state lookup. It validates
the canonical provider fingerprint, explicit DER trust, credential identity, frozen
message and timeout before connecting; implicit TLS input is rejected.

The existing canonical SMTP acknowledgment protocol distinguishes input/auth/TLS
failure, submission phase and acceptance. A successfully written failure acknowledgment
can exit 0: child process success alone is never delivery evidence. Malformed frames
produce `SMTP_SUBMIT AUTH INPUT` and a newline with empty stderr. Parent permission
guards and acknowledgment classification remain mandatory. Parent supervision bounds
DNS/TLS/socket lifetime and cleans up the child. Installed loopback acceptance proves
missing STARTTLS produces a sanitized refusal without transmitting AUTH in plaintext.
Installed helper acceptance also verifies STARTTLS/AUTH and a temporary final DATA
refusal followed by relay acceptance from a fresh helper process using identical
frozen bytes. This is helper replay, not installed monitor/store restart acceptance;
installed monitoring acceptance now includes verified TLS submission and restart.

## Foreground activation (2026-10-24)

`start --foreground --config <absolute-path>` accepts exactly these words/options in
any order, with no duplicates or extra values. `start --help` and `--help start` use
`start-help.stdout` without resource access. Global help intentionally adds start.
The command is implemented on Linux/macOS and accepts webhook-only, SMTP-only
and mixed configurations. Webhook-only runs require no SMTP limits or permissions.
Missing webhook resources still exit 2 before state creation.

Startup reads one protected snapshot. Slurm programs resolve once from PATH with
at most 4,096 bytes and 64 absolute directory entries; missing programs exit 2
before state creation. Configured query timeout also bounds SQLite busy waits.
Configured poll cadence remains completion-relative, including blocked delivery.
An internal renewable poll batch retains one owner and does not limit run duration.

Diagnostics are static and omit private resources. Successful start emits
`Foreground monitoring started.` to stderr. Shutdown emits
`Foreground monitoring stopped by SIGINT.` / `... SIGTERM.` with exit 130/143.
Corrupt state/runtime failures stop with exit 1. Missing config/resources exit 2.
Denied delivery stays pending with no consumed attempt; it reports a blocked line
and waits configured cadence. `config validate` retains its finite exit-3 policy.

Health uses stdout with labelled sampled pending/failed counts, stale status and
truncation; it makes no exact-total claim. See [ADR 0065](../../docs/adr/0065-installed-smtp-mixed-foreground-command.md)
for lifecycle, error, cleanup and compatibility details. Installed accepted SMTP
submission and no-replay restart have controlled TLS acceptance; no real-cluster/
provider or supported-release claim follows.

## Doctor

`doctor --config <absolute-path>` and its resource-free help use the same finite
option grammar as status. Checks protected config/trust/credentials and exact SMTP
permission, then bounded `squeue --version` and `sacct --version` probes. It sends
nothing and creates no state. Success labels state uninspected; historical status
remains separate. Outputs are static and exclude raw probe text. Missing config or
programs exit 2, SMTP permission denial 3, unsuccessful/empty/over-budget probes 1;
success exits 0 with `doctor-success.stdout`. Shared timeout/output budgets and
scope are recorded in [ADR 0068](../../docs/adr/0068-installed-read-only-doctor.md).

## Explicit provider test

`test <provider-name> --config <absolute-path>` authorizes exactly one synthetic
request to the selected alias, regardless of route event selection. Configuration
options may surround the command/alias pair. Preview goes to stdout before sending;
webhook preview includes the exact JSON, SMTP preview includes its test subject/body.
No scheduler, state creation, enrollment or automatic retry occurs. SMTP exact-pair
permission is checked before credentials. Missing resources/alias exit 2, denied
SMTP permission 3, unacknowledged transport 1 and acknowledged acceptance 0 with
`test-success.stdout`. Failure may leave acceptance unknown; it never establishes
human receipt. `test-help.stdout` is resource-free. See [ADR 0069](../../docs/adr/0069-explicit-one-shot-provider-tests.md).

## Interactive configuration review

`init --config <absolute-path>` uses finite command grammar and resource-free
`init-help.stdout`. Terminal stdin is required; otherwise exit 2 before access.
Enter the absolute path to a protected draft JSON file. Review policy, transmitted
fields, safe provider identity and exact current SMTP pairs. Literal `yes` enrolls
those pairs into a new mode-0600 file and emits `init-success.stdout`; any other
complete answer cancels with exit 0 and no file. Historical permission entries are
not retained. Settings are explicit, with no filled operational defaults.

Existing targets/symlinks, unsafe parents or invalid resources/input fail with exit
2. No parent directories are created. Publication is atomic and refuses concurrent
replacement; write failure exits 1 and may require inspecting a complete destination
after sync failure. No provider request, credential lookup for SMTP, scheduler/state
activity or monitoring occurs. See [ADR 0070](../../docs/adr/0070-protected-interactive-config-review.md).

### Filesystem publication failures

On unsupported no-replace rename (`ENOSYS`, `EINVAL`, `EOPNOTSUPP`), init uses
same-directory atomic hard-link publication and removes its temporary name before
success. Existing targets are never replaced. File/directory sync remains required;
no new config keys or dependencies are introduced. See [ADR 0072](../../docs/adr/0072-portable-no-overwrite-configuration-publication.md).

Exit 1 diagnostics now distinguish:

- `Configuration file sync failed; no new configuration was published.`
- `Atomic configuration publication failed; inspect the destination before retrying.`
- `Configuration was published but temporary-link cleanup failed; inspect links before use.`
- `Configuration was published but directory sync failed; inspect it before use.`

Other write errors retain the existing generic diagnostic. A crash between link
and unlink can leave a two-link file that protected readers reject. Inspect it
while setup is stopped; never relax permissions/link validation to force acceptance.

## Slack provider addition (2026-10-25)

The existing commands accept explicit Slack providers using the same config grammar.
Help/start help deliberately name Slack. Init labels Slack with a safe origin and
`fields=cluster_id,job_identifier,state,observed_at,event_id rendering=plain_text_v1`.
`test <alias>` previews `type=slack payload=<JSON>` for Slack, including its synthetic
text; no scheduler/state or automatic retry. Existing exit codes and success text
are unchanged. The private HTTPS helper receives already rendered bounded JSON;
its frame grammar is unchanged. The helper additionally accepts exactly four Slack
fields with disabled formatting/unfurls and a bounded text field ending in the
matching public event ID; other bodies still require the generic event_id binding.
See ADR 0073 for persistence/retry compatibility.

## Foreground failure diagnostics (2026-10-25)

Fatal cycle failures additionally emit `Foreground failure: stage=<stage>
reason=<reason>.` on one line before the existing final message. Stage tokens are
`preflight`, `poll`, `delivery`, `cleanup`, `health`; reason tokens are `capacity`,
`cancelled`, `scheduler`, `storage`, `time`, `policy`, `dispatch_blocked`.
These are internal runtime checks: `policy` does not mean a site administrator
refused permission. First fatal stage wins; ordinary poll/dispatch failures remain
retryable and retain their existing messages. Preparation errors use
`stage=cycle reason=preparation`; revision cleanup uses
`stage=revision_cleanup reason=storage`.

Scheduling errors add `Foreground scheduling failure: reason=<reason>.` with
`policy`, `clock`, `clock_regressed`, `deadline_overflow`, `wait`, `no_progress`,
`wake_limit` or `cycle`. Exit codes, cancellation and recovery behavior are unchanged.
No error objects, private reports, URLs, scheduler output or config values are formatted.
