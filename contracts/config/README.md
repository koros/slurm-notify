# Installed local configuration v1

The local MVP contracts were adopted on 2026-10-13. Installed `config validate`
now supports webhook, required-STARTTLS SMTP and mixed configurations.
`local-v1.schema.json` is the current structural baseline; the earlier webhook-only
schema remains as historical subset evidence. Examples contain synthetic values,
including placeholder permission hashes which authorize no real profile.

Rust additionally enforces strict integer lexemes, duplicate decoded keys, unknown
keys, 65,536-byte/depth-eight/container budgets, route/permission references and
operational cross-field relationships. Config and DER files require absolute
non-symlink paths, owned regular files with mode 0600, owned mode 0700 parents and
safe ancestors. Reads are bounded and reject concurrent metadata changes. No path
search, state creation, account lookup, scheduler or network request is performed.

Webhook environment references must resolve to bounded printable HTTPS URLs with
host and no userinfo/fragment; authorization is bounded printable ASCII. SMTP
checks strict ASCII single addresses, canonical relay/verification host, explicit
trust anchors (32 roots/65,536 total DER bytes), parsed anchors and actual content
fingerprints. Only required STARTTLS is accepted. No system trust fallback.

The current rendering and provider fingerprints must both match an exact enrolled
cluster/destination permission entry. Missing/mismatched permission exits 3 before
that profile's credential lookup; resource/config failure exits 2. Earlier providers
may already have had their resources checked. An empty list denies all SMTP profiles.
Credential username must exactly match configured identity and be 1..64 printable
ASCII bytes; password must be 1..128 printable ASCII bytes. A rejected username
prevents password lookup. No credential or private endpoint/path appears in output.
Success reports schema version, safe cluster alias, provider count and
`smtp_permissions=approved` (or `not_applicable` when no SMTP provider exists).
This validates current profiles only, not pending historical database profiles.

Permission hashes are computed from explicit rendering metadata, canonical provider
metadata, local resource references and actual trust fingerprints using the existing
versioned codecs. Changing a recipient, disclosure, relay or trust content requires
new exact enrollment. There is no implicit enrollment or retargeting. Interactive `init` computes and displays current pairs, then enrolls them only
after explicit confirmation into a new file. It does not retain historical pairs
or overwrite an existing configuration. Manual hash calculation is unnecessary.

The examples' numeric values are not defaults or polling-policy recommendations.
OS environment lookup allocates before accepted-byte checks and has no promised
hard startup deadline. Validation cannot prove TLS handshake/relay acceptance or
human receipt. Historical `status` inspects existing state without resolving provider
resources. Foreground monitoring, explicit provider tests, doctor and interactive init are installed.

Compatibility: this unreleased 0.0.0 increment replaces the explicit unsupported-SMTP
exit-2 diagnostic with supported validation and exact-permission exit 3. Global and
command help are updated deliberately; existing webhook success/version/invocation
outputs remain stable. Baselines are never regenerated by tests.

### Explicit webhook trust (2026-10-24)

An optional `trust_der_files` on a webhook provider replaces bundled public roots
with 1..32 explicit protected DER certificates, at most 65,536 bytes total. The
same ownership, permissions, symlink and certificate validation used for SMTP
applies. Absence retains bundled public roots; an empty or invalid list fails.
Hostname verification is always enabled. Custom trust fingerprints participate in
endpoint revisions; changing trust blocks old pending frames instead of retargeting
them. No old default-root revision changes. The structural schemas deliberately
add this optional field without changing version 1 or existing examples.

### Slack incoming webhooks (2026-10-25)

Provider `type: "slack"` uses the same required/optional settings as `webhook`,
with deterministic plain text rendering instead of the generic event JSON.
`slack-v1.example.json` is a complete example without credentials. The URL is loaded
from an environment reference; no Slack bot token/channel override is required.
Both canonical/rendered payloads must fit `payload_limit_bytes`; text is capped
at 4000 bytes. Setup previews its disclosed fields; explicit tests preview the
actual Slack JSON. A versioned destination revision prevents reinterpreting pending
webhook work as Slack or vice versa. Existing generic/SMTP baselines are unchanged.
See [ADR 0073](../../docs/adr/0073-slack-incoming-webhook-rendering.md) and
[setup](../../docs/operations/slack.md).
